# 냉장고 배치 카탈로그

## 조사 범위와 현재 상태

2026-10-22 기준 제조사 제품 페이지·구매 안내·설명서·사양서에서 확인한 가정용 대표 구조를 정리했다.
전 세계 모든 모델을 망라한 목록은 아니다. 확인한 구조와 추가 확인할 구조를 구분하고 새로운 사례를 계속 추가한다.
단종 제품도 현재 사용 중일 수 있으므로 구조 사례로 유지한다. 판매 여부·가격·용량은 이 카탈로그의 관리 대상이 아니다.

- 데이터: `src/features/fridge/model/fridgeLayoutCatalog.json`
- 검사: `node scripts/validate-fridge-layout-catalog.cjs`
- 조사 JSON은 화면에 직접 연결하지 않는다. 등록 화면은 사용자가 단별 문 개수를 정해 입력 구성을 만든다. 실제 저장은 아직 연결하지 않았다.
- 일반 냉장고, 냉동고, 김치냉장고, 가정용 하부장 서랍형을 조사했다. 와인·음료 전용 온도 구역과 업소용·차량용·캠핑용·연구용 기기는 이번 범위에서 제외했다.

## 현재 등록 방식

등록은 두 단계로 나눈다. 1단계는 이름·단별 문 배치, 2단계는 문 수납·본체 연결·내부 칸 설정이다.
유형을 고르는 대신 단을 추가·삭제하고, 각 단의 문 개수를 `− / ＋`로 조절한다. 문은 단 안에서 가로로 나란히 배치하며 전체 도어 수 문구는 따로 표시하지 않는다.
초기값은 2단·단별 문 1개이며, 최소 1단·단별 문 1개를 유지한다. 입력 범위는 최대 3단·단별 문 3개이다.
닫힌 도식은 기본 표시용 외곽 비율을 가로 3:세로 5로 두고, 내부를 단 수에 맞춰 나눈다. 단 이름은 도면 왼쪽, 문 개수 조절·단 삭제 버튼은 오른쪽에 각 단의 중앙 높이로 배치한다. 좁은 화면에서는 도면 너비를 줄이고, 단이 많으면 버튼이 겹치지 않도록 높이를 확보한다. 실제 제품의 높이·너비 비율을 추측하지는 않는다. 세로로 단을 가로지르는 문 합치기와 홈바·작은 보조 포켓은 이번 범위에서 제외한다.

문마다 독립 본체 하나와 문 수납의 위칸·아래칸을 기본 생성한다. 본체에는 기본 칸 하나를 포함하고 냉장·냉동 모드는 선택 전까지 `null`로 둔다.
2단계는 모든 단의 문·본체를 하나의 열린 도면으로 표시한다. 맨 위 공통 영역 이름 대신 연결된 문·본체 사이에 위아래 회색 경첩을 표시한다. 같은 쪽의 여러 문이 공용 본체에 연결되면 다른 문을 가로지르지 않도록 단의 바깥 여백으로 연결하며, 서랍형에는 경첩을 표시하지 않는다.
`FridgeMap`의 칸 표시·영역 선택 강조를 재사용하며, 도면의 문이나 본체를 누르면 아래 편집 폼이 해당 영역으로 바뀐다.
도면에는 본체의 단·위치 문구와 재료 개수를 표시하지 않는다. 아래 편집 제목은 `본체 → 1단`처럼 영역 다음에 위치를 표시한다.
폭은 단마다 독립적으로 계산해 해당 단 전체를 채운다. 다른 단의 문 개수·여는 방식 때문에 좌우 빈 열을 예약하지 않는다.
각 본체의 왼쪽 열림 문·본체·오른쪽 열림 문을 한 묶음으로 배치하며, 같은 방향의 문을 단의 양끝으로 모으지 않는다. 공용 본체는 연결된 문들을 해당 본체 좌우에 모은다.
문이 많아 좁아진 영역은 프레임·칸 여백을 줄이고 이름을 최대 두 줄로 표시한다. 전체 이름은 영역 선택 후 아래 편집 폼에서 확인한다.
여닫이 문 하나와 해당 독립 본체는 같은 폭이며, 여러 여닫이 문이 본체 하나를 공유하면 그 문들의 폭 합이 해당 본체 폭과 같다. 모두 서랍형인 단은 본체만으로 전체 폭을 채운다.

여는 방식은 `왼쪽 열림 / 오른쪽 열림 / 서랍형` 중에서 각 문마다 정한다. 문 개수·위치로 여는 방식을 자동 확정하지 않는다.
문을 누르거나 연결된 본체를 선택해 여는 방식을 변경할 수 있다. 공용 본체는 연결된 문마다 선택지를 표시한다.
서랍형은 옆으로 펼친 문과 문 수납 위치를 표시하지 않고 본체를 표시한다. 문 수납을 선택하다 서랍형으로 변경하면 해당 본체로 선택을 옮긴다.
서랍형으로 바꿔도 기존 문 식별자·열림 방향·수납 사용 여부·칸 입력·본체 연결은 보관한다. 본체에서 여닫이로 되돌리면 해당 문의 수납 설정이 복원된다.
여닫이 문에서는 수납 사용 여부를 독립적으로 정한다. 방향을 바꿔도 문 식별자·칸 입력·본체 연결은 유지한다.
문 수납을 끄면 문 전체에 두 대각선의 X와 `수납 없음`을 표시하며, 문을 숨기거나 도어 수를 줄이지 않는다.
수납 없는 문도 눌러 다시 선택할 수 있다. 해당 문의 칸 편집과 배치도 위치는 숨기되 기존 칸 입력은 보관하여 수납을 다시 켰을 때 복원한다.

같은 단에서 오른쪽 이웃 본체와 합칠 수 있다. 문 개수·문 수납·문 방향은 그대로 두고, 두 본체의 칸을 왼쪽부터 이어 붙인다.
합친 칸이 5개를 넘으면 합치기를 제한한다. 두 본체의 보관 모드가 같으면 유지하고 서로 다르면 미선택으로 바꿔 재선택한다.
공용 본체를 문별로 다시 분리할 수도 있다. 기존 칸은 첫 본체에 모두 남기고, 나머지 본체에는 기본 칸 하나를 만들며 기존 보관 모드를 이어받는다.
본체 연결은 같은 단에서만 가능하며 세로 병합은 제공하지 않는다.

영역별 칸 수는 `− / ＋`로 1~5개까지 조절하고 이름은 최대 24자로 입력한다. 마지막 칸부터 추가·제거하며 다른 문·본체의 입력은 유지한다.
본체 칸의 일반 칸·서랍 1개·서랍 2개는 기존 `SlotStructureSelector`를 재사용한다. 좌우 서랍은 같은 칸 ID와 서로 다른 서랍 번호로 구분하며 문 수납에는 자체 서랍을 설정하지 않는다.
보관 모드는 본체마다 냉장·냉동을 선택하며, 문을 편집 중에도 연결된 본체의 모드를 변경한다. 같은 모드를 선택한 다른 본체와 자동으로 합치지 않는다.

단·문을 추가할 때 새 식별자를 발급하고 남은 문·본체의 식별자와 입력은 유지한다. 단을 삭제한 뒤 다시 추가해도 삭제된 위치의 식별자를 재사용하지 않는다.
각 단에서 문을 줄이면 마지막 문을 제거한다. 공용 본체에 연결된 마지막 문을 제거해도 다른 문이 남아 있으면 본체의 기존 칸·모드는 유지한다.
단계를 바꾸면 스크롤은 맨 위에서 시작하며, 이동 버튼은 스크롤 영역 밖 하단에 고정한다. `이전`과 기기의 뒤로가기는 입력을 유지한 채 1단계로 돌아간다.
1단계의 `취소`는 홈으로 돌아간다. 현재 등록값은 화면 상태에서 관리하며 DB 저장은 아직 연결하지 않았다.

## 보관 중인 간소화 데이터

`src/features/fridge/model/fridgeLayoutPresets.json`은 이전 구조 선택 화면에서 사용하던 간소화 데이터이며 현재 등록 화면에는 연결하지 않는다.
조사한 21종 중 물리적 배치·문 연결이 같은 항목을 합친 15종을 그대로 보관한다. 이전에 보류한 6종의 `enabled: false`와 `disabledReason`도 유지한다.
`layout`은 본체 배치, `compartments`는 본체 공간, `openings`는 대표 사례의 외부 문 연결이다. 대표 사례의 여닫이·서랍 형태를 사용자 냉장고의 고정 규칙으로 적용하지 않는다.
원본 조사 JSON의 21종·출처·추가 조사 항목도 유지하며, 실제 사용자의 등록값과 분리한다.

## 데이터 읽는 방법

`templates`는 물리적 배치, `sources`는 제조사 근거, `variations`는 배치를 새로 만들지 않고 처리할 변형이다.
`schemaVersion`은 데이터 형식, `catalogRevision`은 전체 자료의 개정 번호, 각 `revision`은 개별 유형의 개정 번호이다.

- `layout`: 행마다 열 수가 같은 격자. 현재 유형은 2열을 사용하며 새 배치에 맞춰 열 수를 늘릴 수 있다. 같은 실 ID가 두 셀에 있으면 하나의 넓은 본체이다. 행·열은 위치만 나타내며 실제 크기 비율이 아니다.
- `view`: `FRONT`는 정면, `TOP`은 위에서 본 배치이다.
- `compartments`: 물리적 보관 공간. 각 공간에는 본체를 기본 포함하고 내부 선반·서랍은 사용자가 구성한다.
- `openings`: 외부 여닫이 문(`HINGED`), 서랍(`DRAWER`), 뚜껑(`LID`). `compartmentIds`로 연결할 본체를 지정한다.
- `doorBins`: `CONFIGURABLE`이면 문 수납 영역의 사용 여부를 선택할 수 있다. 실제 수납칸 존재를 보장하지 않는다. `NONE`이면 문 수납 영역을 만들지 않는다.
- `referenceRole`: 대표 모델에서 확인한 용도. 물리적 위치 ID나 사용자가 선택한 현재 모드로 사용하지 않는다.
- `modeOptions`: 대표 모델에서 확인한 보관 모드의 앱 분류. `null`은 미확인이며 빈 배열로 대체하지 않는다. 배열에도 제조사의 익힘·음료·육류 등 모든 세부 모드를 나열하지는 않았다.
- `sourceIds`: 해당 유형의 근거. 각 출처의 `checkedOn`과 `evidence`에 확인 날짜와 확인 내용을 남긴다.

예를 들어 상단 공용·하단 좌우형의 `layout`은 다음과 같다.

```json
[
  ["upper", "upper"],
  ["lower-left", "lower-right"]
]
```

상단 왼쪽 문과 오른쪽 문은 모두 `upper`에 연결된다. 본체를 두 개 만들지 않는다.
하단 좌우는 다른 ID를 사용하므로 보관 모드가 같아져도 같은 실로 합쳐지지 않는다.
반대로 외부 1도어 내부 냉동칸형은 문 하나가 냉장·냉동 두 공간에 연결된다.

## 모델별 차이와 앱 연결 시 지킬 경계

이 자료는 브랜드나 제품명으로 모든 사양을 자동 확정하는 제품 DB가 아니다.
같은 외형이어도 전환 가능한 실·문 수납·선반 수가 다를 수 있다.
예를 들어 Samsung RF23DG9600SRAC의 하단 오른쪽 전환 기능을 모든 4도어 냉장고의 규칙으로 적용하면 안 된다.
출처의 확인된 모드는 대표 모델 안내에 사용하고, 구조만 고른 사용자의 다른 모델에 그대로 제한을 걸지 않는다.

등록 초안의 문·본체는 사용자의 배치 구성에 따라 식별자를 발급하며 표시 위치는 단·문 순서에서 구한다. SQLite는 `CHILLED | FROZEN`만 저장하며 초안의 미선택 모드 `null`은 저장할 수 없다.
카탈로그의 김치·특수 냉동 모드나 다단·좌우 배치가 이미 저장·표시된다는 뜻이 아니다.
제빙 서랍은 위치 자료에 포함하지만 일반 재료를 등록할 수 있는지는 별도로 결정해야 한다.

다음 구현은 사용자가 구성한 입력 초안의 저장을 연결하는 단계이다.
카탈로그와 실제 등록값은 분리한다. 저장된 냉장고의 UUID·구조·입력값을 유지해 카탈로그 추가·수정이 기존 냉장고를 바꾸지 않도록 한다.
문 수납 선택, 내부 칸 편집, 저장 기능은 기존 공통 컴포넌트와 `Refrigerator → Compartment → Area → Slot` 구조를 우선 재사용한다.

## 새로운 사례 추가 절차

1. 제조사 설명서·실제 내부 사진·제품 사양에서 외부 문과 내부 본체의 대응 관계를 확인한다.
2. 기존 구조와 같으면 `examples`, `sourceIds`, 필요한 `notes`를 보강한다. 경첩 방향·색상·용량·내부 선반 수만 다르면 새 유형을 만들지 않는다.
3. 구조가 다르면 변경되지 않을 새 `id`로 유형을 추가한다. 모드는 실제로 확인한 범위만 기록하고 미확인은 `null`로 남긴다.
4. `sources`에 링크·제조사·확인 날짜·확인 내용을 추가한다. 내부 구획을 확정하지 못하면 `pendingCases`에 추가한다.
5. 해당 유형의 `revision`, 전체 `catalogRevision`, `researchedOn`을 갱신하고 이 문서의 구조 표를 맞춘다. 기존 ID를 다른 구조에 재사용하지 않는다.
6. 카탈로그 검사, lint, TypeScript 검사를 실행하고 출처를 다시 대조한다.

```bash
node scripts/validate-fridge-layout-catalog.cjs
npm run lint
node node_modules/typescript/bin/tsc --noEmit
```

검사 스크립트는 ID 중복, 잘못된 출처·모드·문 연결, 도식에서 누락된 실, 끊어지거나 직사각형이 아닌 본체를 검사한다.
제품 구조의 사실 여부와 실제 기기 화면은 자동 검사의 대상이 아니다.
자료는 저장소에서 수동으로 추가하고 앱 업데이트에 포함한다. 자동 수집·원격 배포·정기 조사 기능은 구현하지 않았다.
